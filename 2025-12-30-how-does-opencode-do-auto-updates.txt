● OpenCode has a two-tier auto-update system: one for the CLI and one for the Desktop (Tauri) app.

  CLI Auto-Updates

  Entry point: packages/opencode/src/cli/upgrade.ts:6-25

  The upgrade check runs at startup (in cli/cmd/tui/spawn.ts:16) before the server initializes:

  1. Detects installation method (npm/pnpm/bun/brew/curl) based on executable path
  2. Fetches latest version from the appropriate source:
    - Homebrew: https://formulae.brew.sh/api/formula/opencode.json
    - NPM/PNPM/Bun: NPM registry for the current channel
    - Curl: GitHub releases API
  3. Compares current version to latest (simple string equality)
  4. If update available, either auto-installs or notifies based on config

  Configuration options (config.ts:684-689):
  - autoupdate: true — Auto-download and install (default)
  - autoupdate: false — Disable update checks
  - autoupdate: "notify" — Show notification without auto-installing
  - Env var OPENCODE_DISABLE_AUTOUPDATE also disables updates

  Installation methods (installation/index.ts:121-161):
  case "curl":  cmd = $`curl -fsSL https://opencode.ai/install | bash`
  case "npm":   cmd = $`npm install -g opencode-ai@${target}`
  case "pnpm":  cmd = $`pnpm install -g opencode-ai@${target}`
  // etc.

  Desktop (Tauri) Auto-Updates

  Uses the Tauri updater plugin with signature verification:

  Endpoint: https://github.com/sst/opencode/releases/latest/download/latest.json

  Flow (desktop/src/updater.ts:9-47):
  1. Check for update via Tauri's check()
  2. Download update in background
  3. Show confirmation dialog to user
  4. On Windows, kills sidecar process first
  5. Install and relaunch app

  The updater is only enabled when built with TAURI_SIGNING_PRIVATE_KEY present (src-tauri/src/lib.rs:189).

  Recommended Implementation

  Add path-based detection first (most reliable), then fallback to command checks:

  Then add command-based fallback checks to the checks array:

  {
    name: "scoop" as const,

  },
  {
    name: "choco" as const,

  },

  2. Upgrade commands (upgrade() function)

  Add cases to the switch statement:

  case "scoop":
    cmd = $`scoop update opencode`
    break
  case "choco":
    cmd = $`choco upgrade opencode -y --no-progress`
    break

  3. Latest version (latest() function)

  For both Scoop and Chocolatey, the simplest approach is to use the GitHub releases API (which is already the default fallback). However, you could add specific sources:

  // Chocolatey API
  if (detectedMethod === "choco") {
    return fetch("https://community.chocolatey.org/api/v2/package-versions/opencode")
      .then((res) => res.json())
      .then((versions: string[]) => versions[0]) // Latest is first
  }

  // Scoop - use GitHub releases (already the default fallback)
  // Scoop manifests track GitHub releases anyway

  Key Considerations

  | Aspect          | Scoop                     | Chocolatey                       |
  |-----------------|---------------------------|----------------------------------|
  | Path detection  | scoop\apps\opencode       | chocolatey\lib                   |
  | List command    | scoop list opencode       | choco list --local-only opencode |
  | Upgrade command | scoop update opencode     | choco upgrade opencode -y        |
  | Version source  | GitHub releases (default) | Chocolatey API or GitHub         |
  | Requires admin  | No                        | Often yes                        |

  Potential Gotcha: Chocolatey Admin Rights

  Chocolatey upgrades often require admin privileges. You may want to handle this:

  case "choco":
    // Check if running as admin, otherwise warn
    cmd = $`choco upgrade opencode -y --no-progress`
    break

  Or detect elevation failure and emit a notification instead of auto-upgrading.
